## 실행 환경과 데이터 보존

```powershell

```

이미 서버가 살아 있으면 중복 실행하지 않습니다. 먼저 `http://127.0.0.1:4173/api/guests` 또는 `/guestbook/`의 응답을 확인합니다.

- 8회차 종료 때 서버: PID **2648**, `node server.mjs`. 9회차에서는 기존4173 서버의 API 정상 응답과 실제0명을 확인했으며 서버 코드는 바꾸지 않아 재시작하지 않았습니다. PID는 참고값이며 재시작이 필요하면 반드시 다시 확인합니다.
- 로그: `server-handoff.log`, `server-handoff-error.log`. Node의 SQLite experimental 경고는 있었으나 앱 오류는 없었습니다.
- 실제 방명록: `data/garden.sqlite` 및 WAL 관련 파일. **이 디렉터리를 보존합니다.** 마지막 조회는 실제 등록 0명입니다. 화면의 24명은 예시 하객이며 실제 등록 카운트와 분리됩니다.
- 설정: `PORT`, `GARDEN_DB`, `INVITATION_URL`, `NODE_ENV=production`. HTTPS, 영구 저장소, 공개 접속 등 인터넷 배포 작업은 아직 완료하지 않았습니다.

- 실제 앱과 원본 서비스에는 테스트 메시지를 쓰거나 기존 데이터를 수정하지 않습니다. 쓰기 검증은 격리 DB와 별도 포트를 사용합니다.

이전 서버 PID24404는 대화 중단 후 종료된 것을 발견했습니다. 최종 서버2648은 Node의 detached child + stdio 파일 리디렉션 + unref로 다시 실행했습니다. 서버가 종료되면 프로젝트의 원래 서버를 재실행합니다. 미리보기를 살리기 위해 저장 API가 없는 임시 정적 서버로 대체하지 않습니다. 프로세스를 종료할 때는 해당 PID의 경로·명령줄과 프로젝트 관련성을 먼저 확인합니다.

## 완료한 기능과 직전 수정

현재 의상16·헤어16·장신구15+없음·피부6·동작8을 제공합니다. 안경·헤어핀·귀걸이·손 소품 등 서로 다른 부위를 함께 선택할 수 있고 같은 부위는 교체합니다. 4종 손 소품은 모든 동작·걷기·좌우 반전에서 같은 손의 접점을 유지합니다. 귀걸이는 양쪽을 따로 헤어별 귓불에 맞췄고 4종 머리핀은 머리 안에 부착되도록 수정했습니다.

서버 저장, 본인 편집/삭제, 15초 목록 동기화, 검색/필터, 추가 목록, 예시 하객, 키보드/조이스틱/패드, 클릭 경로, 확대/축소, 내 위치/제단 이동, 설정, 월드 확장 등이 구현되어 있습니다. 상세 판단은 기능 비교표를 따릅니다.

마지막 9회차에서 완료한 변경:

1. **밝은 옷 색상 명암 복원.** 크림·라일락 등 밝은4색에서 흰 면으로 사라지던 리본·주름·재킷 절개선을 살리도록 밝은 명암을 압축했습니다. 원본룩768개와 어두운4색384개 비교 결과는 동일하며, 머리·피부 RGB와 몸체/동작 알파는 변하지 않았습니다.16의상×6피부×8색×색변경 여부=1536 sprite,2048 동작 전후 렌더 비교 및32대표 조합 시각 검토를 통과했습니다.
2. **신규 등록 응답 유실 복구.** POST는 저장됐지만 응답이 유실된 뒤 메시지를 바꾸면409가 반복되던 문제를 수정했습니다. 신규 등록 실패 시 목록 조회로 본인을 복구하며 작성 중 form/draft는 보존합니다. 다음 명시적인 제출은PATCH로 처리합니다. 복구조회 실패/본인없음은 요청키를 유지합니다. 제출 시작에 이전GET 응답도 무효화합니다.
3. **정원 복귀 키보드 초점.** 상세의 ‘정원에서 만나기’와 성공화면의 ‘정원에서 내 모습 보기’가 정원에 초점을 옮겨 바로 방향키를 쓸 수 있습니다. 모바일목록·데스크톱카드·등록완료3경로에서 실제 이동까지 검증했습니다.

8회차에서 완료한 변경도 보존했습니다:

1. **모달 배경 렌더 낭비 감소.** 모달60프레임에서 같은 배경 render/stop이 각각60회이던 것을 진입1회와 필요한 갱신으로 줄였습니다. resize·이미지·글꼴·데이터·카메라/설정 변경은 invalidate합니다. 숨긴 문서와 복귀, 닫은 뒤 시간 점프 방지, 미리보기의 독립 동작을 검증했습니다. RAF 자체가 중단되는 것은 아니며 모바일FPS/배터리 개선 수치로 주장하지 않습니다.
2. **삭제 성공 응답 유실 복구.** 이미 없는 메시지 전체 DELETE는200 성공으로 처리해 재시도 시 확인창/본인 UI가 정상 정리됩니다. 존재하는 타인 메시지403, 없는 메시지 수정404는 유지됩니다. 실제 브라우저에서도 삭제 후 서버0명 + 프록시503 → 재시도 성공·방문객 복귀를 확인했습니다.
