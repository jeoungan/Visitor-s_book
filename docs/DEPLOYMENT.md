# 웨딩 가든 배포 지침

이 문서는 2026-09-21 사용자가 “GitHub Pages에서 앱 대신 문서가 보인다”고 알려 준 문제의 원인과 재발 방지 기준을 기록한다. 절차를 적은 문서이며, 그 자체가 배포 성공의 증거는 아니다. 현재 배포 결과는 해당 커밋의 GitHub Actions 실행 결과와 실제 공개 화면으로 확인한다.

공개 앱 주소: [강정이네 웨딩 가든](https://jeoungan.github.io/Visitor-s_book/)

저장소: [jeoungan/Visitor-s_book](https://github.com/jeoungan/Visitor-s_book)

## 앱 대신 README가 나온 이유

GitHub Pages가 브랜치 게시 방식으로 `main`의 저장소 루트(`/`)를 게시하고 있었다. 루트에는 `README.md`가 있고 앱의 진입 파일인 `index.html`은 `public/` 안에 있었다. 이 설정은 실제 앱을 진입점으로 게시하지 않아 README가 사이트 화면으로 표시되는 결과를 만들었다.

기존 앱에는 `/assets/...` 같은 서버 루트 기준 경로와 Node 서버의 `/api/...` 호출도 있다. 따라서 파일 위치만 바꾸거나 `public/`을 복사하는 것으로는 프로젝트 사이트 경로 `/Visitor-s_book/`와 서버 기능까지 해결되지 않는다. 정적 사이트용 경로 처리와 서버 없는 실행 방식이 함께 필요하다.

GitHub에 소스를 푸시하는 작업과 사용자가 접속할 앱을 배포하는 작업은 별개다. 앞으로는 실제 공개 URL에서 앱을 확인하는 단계까지 배포 작업에 포함한다.

## 두 실행 방식

| 항목 | GitHub Pages | Node 서버 |
| --- | --- | --- |
| 목적 | 인터넷에서 바로 열 수 있는 정적 앱 | 방문자가 함께 사용하는 방명록 서버 |
| 앱 진입 | `/Visitor-s_book/`, `/Visitor-s_book/guestbook/` | `/guestbook/` |
| 실행 환경 | 브라우저, 정적 HTML·JS·CSS·이미지 | Node.js 24 이상과 SQLite |
| 방명록 저장 | 사용하는 브라우저의 로컬 저장소 | 서버의 `data/garden.sqlite` 또는 설정한 DB |
| 다른 기기와 공유 | 공유되지 않음 | 같은 서버 DB를 통해 공유 |
| 운영상 필요한 설정 | Pages artifact와 프로젝트 기본 경로 | HTTPS, 외부 접속 설정, 영구 저장 볼륨 |

Pages의 로컬 저장은 같은 브라우저에서 저장·재접속하는 데 사용한다. 다른 방문자, 다른 기기, 다른 브라우저에는 전파되지 않으며 사이트 데이터가 삭제되면 사라질 수 있다. Pages에서 앱이 열린다는 이유로 공유 방명록까지 구현 또는 배포 완료라고 말하지 않는다.

기존 서버 모드는 계속 유지한다. 공유 방명록을 공개 운영하려면 Node 서버를 실행할 호스팅과 영구 저장소를 마련하고, 별도 브라우저에서 작성한 메시지가 다른 브라우저에도 보이는지 검증한다.

## Pages 게시 계약

Pages 설정은 GitHub Actions가 업로드한 정적 빌드 artifact를 배포하도록 한다. README가 있는 저장소 루트를 그대로 게시하는 브랜치 설정으로 되돌리지 않는다.

배포 workflow는 `.github/workflows/pages.yml`이다. `npm run build:pages`가 `node tools/build_pages.mjs`를 실행하여 `public/`의 실행 파일과 필요한 자산을 `dist/`에 만든다. workflow는 `dist/`의 내용을 Pages artifact로 업로드한다.

소스의 서버 실행 방식과 구분하여 프로젝트 기본 경로를 적용한다. 빌드 결과의 `dist/index.html`과 `dist/guestbook/index.html`은 같은 앱으로 연결한다. 최종 artifact의 최상위 파일이 `index.html`이어야 하며, `public/index.html` 또는 `dist/index.html`이 한 단계 더 안쪽에 들어간 채 업로드해서는 안 된다.

Pages 빌드의 `garden-storage=local` 메타 설정은 브라우저 저장 방식(`createBrowserStorage`)을 선택한다. 이 설정을 서버 모드 HTML에 임의로 적용하지 않는다. Node 서버 모드의 API와 SQLite 저장 방식은 별도로 유지한다.

배포에 포함할 항목:

- 앱의 `index.html`, JavaScript 모듈, CSS와 정적 실행 설정
- `/guestbook/` 직접 진입에 필요한 진입 파일
- 화면에 실제 사용하는 이미지, 아틀라스, 피부 마스크와 manifest
- 정적 파일을 의도한 그대로 게시하기 위한 설정 파일

배포에서 제외할 항목:

- 실제 DB와 `data/`, SQLite 보조 파일, 환경 변수 비밀값
- 서버 코드, 테스트와 내부 인수인계·개발 문서
- 이미지 생성 원본, 생성 경로 메타파일과 중간 처리 파일
- 로그, 캐시와 로컬 화면 검토 산출물

소스 저장소에 개발 자료가 존재하는 것과 공개 사이트 artifact에 포함하는 것은 구분한다. 실행 파일에 필요한 이미지까지 제외하여 빈 canvas를 만들지 않도록 한다.

## 배포 전후 확인 순서

1. 현재 Git 상태, 배포할 커밋, 원격 `main`과 Pages 설정을 확인한다. 사용자 변경을 덮어쓰지 않는다.
2. `npm run check`와 `npm test`를 실행한다. `npm run build:pages`를 수행하고 `dist/index.html`, `dist/guestbook/index.html`, 필수 파일과 제외 대상의 실제 결과를 확인한다.
3. 정적 빌드 결과를 프로젝트 하위 경로 `/Visitor-s_book/`에서 미리 확인한다. 도메인 루트(`/`)에서만 성공하는 것을 충분한 검증으로 취급하지 않는다.
4. 승인된 저장소에 변경 사항을 푸시하고, 해당 커밋을 배포하는 GitHub Actions 실행이 성공할 때까지 결과를 확인한다. 과거 실행의 성공을 현재 커밋의 성공으로 사용하지 않는다.
5. 공개 앱 루트와 `/guestbook/`에 HTTP로 접속한다. 응답이 앱 HTML인지 확인하고 대표 JS·CSS·이미지와 manifest의 정상 응답도 확인한다. 404 문서나 README가 HTTP 200으로 반환될 가능성을 고려해 본문과 진입 요소를 함께 본다.
6. 실제 공개 URL을 브라우저에서 연다. 예식장 canvas, 신랑·신부, 하객이 표시되는지 확인한다. 모바일 세로 화면과 데스크톱에서 화면 비율을 확인하고, 캐릭터 이동과 주요 UI를 조작한다.
7. 콘솔 오류와 실패한 네트워크 요청을 확인한다. 새로고침, `/guestbook/` 직접 진입과 모듈·이미지 캐시 버전도 확인한다. 화면이 오래된 코드라면 버전 쿼리와 실제 배포된 자산 경로를 점검한다.
8. 결과를 인수인계에 기록한다. 배포 커밋, Actions 결과, 확인한 공개 URL, 브라우저 확인 범위와 남은 제약을 남긴다. 사용자에게는 공개 앱 링크와 실제 확인한 결과를 전달한다.

실제 방명록에 쓰기를 하는 검증은 하지 않는다. 서버 저장 기능은 임시 DB를 사용하는 테스트 fixture로 확인한다. Pages 저장 기능을 검증할 때는 테스트용 브라우저 저장소에만 샘플을 만들고 기존 사용자 데이터를 보존한다.

## 잘못된 화면이 나올 때

| 증상 | 우선 확인할 내용 |
| --- | --- |
| README나 문서가 보임 | Pages 게시 원본, Actions artifact 루트의 `index.html`, 현재 배포 커밋 |
| 앱 틀만 보이고 장면은 비어 있음 | JS·이미지·manifest 요청 실패, `/Visitor-s_book/` 기본 경로, 제외된 필수 자산 |
| `/guestbook/` 새로고침이 404 | 실제 `/guestbook/index.html` 제공 여부와 경로 처리 |
| API 요청이 404 | Pages에서 서버 전용 API를 호출하는지, 정적 모드 선택 여부 |
| 최신 변경이 보이지 않음 | 배포 커밋과 Actions 결과, 브라우저 캐시, 자산 URL의 버전 |
| 다른 기기의 메시지가 보이지 않음 | Pages 로컬 저장인지, 공유 서버와 영구 DB가 연결됐는지 |

권한이나 배포 실패가 남아 있으면 정확한 실패 단계와 남은 작업을 보고한다. 저장소 공개 범위나 계정 전체의 정책을 임의로 변경해서 해결하지 않는다. 공개 URL 검증이 끝나기 전에 “배포 완료”라고 기록하지 않는다.
